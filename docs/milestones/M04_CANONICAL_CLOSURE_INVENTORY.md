## Unsafe conversions and derived-byte operations

1. `m04_canonical_json(jsonb)` (lines 4–25) renders numbers using PostgreSQL `value::text`; its use at lines 256–258, 284–292, 344–347, 541–543, 575–577 and 583 can change M03/M04 hash preimages. It cannot be treated as equivalent to frozen `canonicalJsonM03` for arbitrary schema-valid numbers or strings.
2. The bundle trigger reparses retained bytes as `jsonb` at line 236 and deletes root/nested fields before hashing M03 output and logical projections. These are new canonical byte sequences, not necessarily contiguous slices of the stored bundle.
3. The four-family record trigger reparses at line 283 and removes `id`/`recordFingerprint` to recompute IDs and fingerprints. Claim values may contain arbitrary approved field values and exponent-form confidence; raw lexical number/string fidelity is required in those derived preimages.
4. The accepted-result trigger reparses at line 338. Its current core is composed from fixed status and relational IDs, but this narrower value-domain claim still requires schema, canonical-byte, and identity proof; it is not a blanket exemption from the shared predicate.
5. Full closure reparses bundle, evidence, claim, link, completeness, and request payloads at lines 396, 410, 453, 482, 503, 513, 533, 544, 555 and 597. It projects evidence and claims from nested M03 fields/source references, derives completeness and binding IDs, and excludes only the root `idempotencyKey` for the semantic request. A local predicate-only fix would leave this replay/closure path unsafe.
6. Existing structural relations, foreign keys, immutable triggers and row-lock fences are necessary but do not replace byte-level equality. An application-computed hash, `::json` syntax check, `jsonb` value equality, or blanket replacement of `jsonb` with `json` is not an independent canonicality and closure oracle.

## Function/trigger authority graph

`m04_validate_bundle_chunks()` is the deferred trigger for bundle parent/chunk inserts; it calls the canonical predicate and serializer. `m04_validate_canonical_record()` is the deferred trigger for four record tables; it calls the serializer. `m04_validate_accepted_result()` is the deferred result trigger and calls the serializer. `m04_validate_full_binding_closure()` is a deferred trigger on seven binding-family tables and calls `m04_assert_binding_closure(text)`, which itself calls the serializer. `m04_validate_link_lineage()` uses relational columns only. The immutable trigger and predecessor-fence functions are not canonical-byte parsers.

The existing runtime ACL manifest grants M04 exactly four function `EXECUTE` cells: `m03_m04_lock_predecessor_shared()`, `m04_assert_binding_closure(text)`, `m04_canonical_json(jsonb)`, and `m04_payload_is_canonical_json(bytea)`. The other M04 trigger functions are `SECURITY INVOKER` and invoked by installed triggers; the catalog/ACL checks require their existing authority properties. A new helper called from any of these invoker paths requires a separately authorized effective `EXECUTE` route. `PUBLIC EXECUTE`, role-membership expansion, or an unreviewed `SECURITY DEFINER` switch is not an acceptable workaround. The exact additional helper signatures and privilege-cell count cannot be asserted until their complete call graph and projection contract are designed.

## Design gate before another specification

Map the seven surfaces above to a complete canonical-byte validator and projection interface, including derived byte sequences after root/nested field removal. Prove the interface covers exact ECMAScript finite-number rendering, canonical strings including escaped U+0000, Unicode scalar/key ordering, source privacy, and the full-domain negative matrix. Derive each new function signature, its invoker call edges, and each required role/object `EXECUTE` cell from that concrete design. Only then prepare a narrow amendment to the frozen 180-cell authority and associated catalog, migration-ledger, recovery and hostile-role gates for independent specification review and exact owner approval. Until that decision, implementation remains NO-GO and the local migration hash is deliberately not repinned.

A disposable PostgreSQL `17.6-alpine` numeric-format probe under pinned Node `22.23.1` compared 10,012 finite JavaScript values (12 explicit boundaries plus 10,000 deterministic seeded values) to PostgreSQL `float8::text`. Raw spelling differed for 320 of the first 1,012 values, including `1e-7` versus `1e-07` and `0.000001` versus `1e-06`. After reducing both outputs to decimal significand and exponent, all 10,012 samples matched. This is only evidence that a formatting adaptation may be feasible for the sampled domain; it is **not** a proof of full ECMAScript equivalence, canonical acceptance, or any SQL function implementation. The disposable container was stopped.

PostgreSQL 17's [own Ryu configuration](https://github.com/postgres/postgres/blob/REL_17_6/src/common/ryu_common.h#L71-L89) explicitly sets `STRICTLY_SHORTEST` to `0` to avoid exact decimal midpoints, while the [PostgreSQL 17 numeric documentation](https://www.postgresql.org/docs/17/datatype-numeric.html) describes that portability exception. Therefore, matching sampled significands does **not** justify using `float8::text` plus exponent-format adjustment as the complete ECMAScript `JSON.stringify` oracle. A full-domain proof or a separately specified exact algorithm remains necessary.

A second disposable PostgreSQL 17.6 probe targeted 6,376 distinct finite binary64 values around powers of ten, neighboring representable values, exponent thresholds, subnormals, signed zero, and precision boundaries. It found 114 raw-format differences and two differences even after reducing each decimal to its signed significant digits and exponent. Both were the same magnitude with opposite signs: JavaScript renders the binary64 value as `1e+23` (or `-1e+23`), while PostgreSQL renders the **same 64-bit value** as `9.999999999999999e+22` (or its negative). The independent bit check was `44b52d02c7e14af6` on both sides. This is a concrete counterexample to a general `float8::text`-plus-exponent-normalization oracle; it is not itself a demonstrated schema-valid M03 confidence value, so the narrower reachable-domain analysis still matters. The second disposable container was stopped. The earlier 320/1,012 figure was a preliminary raw-spelling subset of a separate 10,012-value probe, not the full population's raw-difference count.

## Preliminary schema-reachable numeric classes

This static map is a feasibility input, **not** a complete parser or equivalence proof. It uses the exact M03/M04 Zod schemas and the SQL's seven persisted byte surfaces; the apparent `z.unknown()` value fields in candidates, final fields, and claims are subsequently checked against the closed `ExtractionValueSchemaByFieldV1` registry. A pinned-runtime check confirmed that Zod `.int()` rejects `1e23` as unsafe and that `[0,1]` confidence rejects it by range.

The remaining numeric question is not answered by a 6,376-value sample or by the `[0,1]` range alone. Any schema-bounded validator still must prove exact ECMAScript rendering for every binary64 confidence value in `[0,1]`, signed zero where accepted, every reachable safe integer, and each derived hash preimage. The eighth amendment expressly forbids assuming that `float8`, `numeric` or `jsonb` reconstruction reproduces the original JavaScript bytes. Its acceptance predicate is defined over the **corresponding schema-valid value**; it does not authorize narrowing any approved schema or ignoring hostile noncanonical tokens.

The explicit M03 numeric leaves include `m02InputProjection.identityDecision.confidenceOrNull` (`m03.ts`), candidate/proposal/field confidence (`m03-bundle.ts` and `m03-values.ts`), fixed analysis-setting literals `0`/`1` and bounded `maxOutputTokens`, M02-projection input-payload byte length, source-reference locator byte/line/ordinal positions, and `analysisAttempts[].tokenCountsOrNull.{input,output,total}` and `.durationMsOrNull`.
