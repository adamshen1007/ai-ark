Approved M04 Section 8 requires every schema-valid M03 bundle to remain bindable and every M04 canonical record to use `canonicalJsonM03` bytes. The M03 serializer uses JavaScript `JSON.stringify` for finite numbers and strings. The current local migration `003` defines `m04_canonical_json(jsonb)` with `WHEN 'number' THEN RETURN value::text` and `m04_payload_is_canonical_json(bytea)` by parsing the payload as `jsonb` and comparing decoded bytes with that reconstruction. PostgreSQL `jsonb` normalizes number spelling: in PostgreSQL 17.6, `('1e-7'::jsonb)::text` is `0.0000001`, whereas `JSON.stringify(1e-7)` is `1e-7`. A valid M03 confidence field may be `1e-7`. The same whole-payload `jsonb` parse rejects a reachable canonical M03 string containing U+0000: the M03 scalar-string schema permits that code point, JavaScript emits its JSON escape `\u0000`, and PostgreSQL rejects that escape in `jsonb`. Consequently, the SQL check can reject valid M03-derived canonical bytes, and SQL-side reconstruction can differ from their hashes. This is an evidence-integrity defect, not permission to narrow the M03 schema, silently transform a bundle, or weaken canonical-byte validation.

## 3. Corrected canonical-byte contract

For each M04 canonical `bytea` payload and every validated M03 bundle carried into persistence, the database acceptance predicate must agree with the exact UTF-8 bytes produced by `canonicalJsonM03` for the corresponding schema-valid value. It must accept valid finite-number renderings, including exponent-form fractions, and all schema-valid JSON string renderings, including U+0000 encoded as `\u0000` in a reachable string value. It must reject alternate lexical spellings of the same value, excess whitespace, key-order changes, malformed UTF-8/JSON, non-finite values, noncanonical number tokens, invalid string escapes, and invalid Unicode scalar sequences. The implementation must preserve the original canonical bytes as authority; it must not round-trip a number through `jsonb`, `numeric`, or `float8` and assume the reconstructed text is the original JavaScript rendering. It must not make a whole-payload `jsonb` parse a prerequisite for accepting valid canonical bytes, because PostgreSQL rejects some schema-valid escaped strings. `jsonb` may assist checks only where its narrower value domain cannot reject an otherwise valid M03/M04 payload; it is neither the sole whole-payload structural oracle nor the sole canonicality oracle.

The exact canonical standard remains the frozen `canonicalJsonM03` behavior: unsigned UTF-8 object-key ordering, original array order, JavaScript finite-number serialization, JSON string escaping, and no undefined/non-JSON value. The correction must cover the full schema-reachable numeric and string domain, not only the two discovered examples. It may replace or refine `m04_canonical_json` and `m04_payload_is_canonical_json` inside `003`, but the database must retain an independently enforced, fail-closed **raw-byte** structural and canonical-payload check; an application-only validation, hash-only check, or permissive JSON parse does not suffice. Stored payload bytes, content IDs, hashes, collision comparisons, immutable-record fences, and reconstruction after restart must remain exact and unchanged in meaning. No new data-retention, source-excerpt, AI, or publication authority is granted.
