It neither authorizes nor performs a commit, shared/production migration, deployment, or M05 work.

## Follow-up integrated-slice attempt (2026-10-16)

A second isolated `postgres:17.6-alpine` container (`--network none`, no host port) tested a scratch raw-byte canonical validator, without modifying migration `003` or the frozen manifest. The validator combined PostgreSQL `json` syntax checking with byte-level string-escape, duplicate-key, unsigned-UTF-8 key-order, whitespace, and number-spelling checks. Its numeric formatter remained a separate scratch function. The scratch validator source was `/tmp/ai-ark-m04-integrated-validator.sql`, SHA-256 `c51baad8bb698e9a3e00c7150eff0dd7d5099c5c15974b59560b8121023b5c32`.

The initial 14-case matrix matched its expected booleans: canonical empty/nested/escaped-NUL/small-number cases were accepted; duplicate and unordered keys at root and nested levels, whitespace, slash escape, `1e0`, `-0`, and a lone surrogate were rejected. A second 13-case matrix also matched: it covered raw UTF-8 key order, escaped printable key, nested array, malformed commas and escape, exponent spelling, `1e+23`, near-one precision, zero, surrogate-pair escape, and canonical/noncanonical control escaping. These 27 hand-selected cases are not a complete canonical-domain proof; the separate 5,696-number result above remains bounded sampling.

The container then created the actual role names `ai_ark_m04_runtime` (NOLOGIN) and `ai_ark_m04_login` (LOGIN), with the latter inheriting the former. A direct `psql -U ai_ark_m04_login -d postgres` session confirmed both `current_user` and `session_user` were `ai_ark_m04_login`. With schema USAGE and EXECUTE on only the scratch validator, the login had no EXECUTE on its numeric helper; `probe.m04_payload_is_canonical_json(convert_to('{"a":1e-7}','UTF8'))` returned **false** despite that input being canonical. Granting the numeric helper EXECUTE to the runtime group inside this disposable container changed the same result to **true**. That diagnostic grant was not added to the repository or its manifest. The false result is caused by the validator's caught permission error, not a canonicality decision.

**Integrated-slice verdict: NOT ESTABLISHED.** The proof did not implement the formatter inside an already-granted function, nested `analysisAttempts` projection, all seven genuine M04 surfaces, unchanged 180-cell catalog, replay/restart, or dump/restore. The scratch role names alone do not establish the actual M04 schema or adapter flow. An end-to-end claim would require a complete inlined/no-new-grant candidate (or a separately approved authority change), followed by fresh real-schema LOGIN, seven-surface, replay, and recovery evidence. M04 remains **NO-GO**. Migration `003` and the manifest retained their pre/post SHA-256 values `3993ab838248720f15e3a0766f95eee9e9d0baaac0af0cad3c9762fb98567501` and `09de293bd6132c124c086d4d3e75a357e6867383d36821602c53e5b496a8a991`.

### Same-day no-new-grant continuation

The numeric formatter was subsequently inlined into the **existing** scratch `m04_payload_is_canonical_json(bytea)` body. A fresh isolated PostgreSQL 17.6 container received migrations `001`, `002`, and the exact local `003` SQL rendered with the unchanged manifest into a real `m04_persistence` schema. Only inside that disposable database, the existing predicate body was replaced with the inlined validator. Direct `psql` as `ai_ark_m04_login` confirmed `current_user=session_user=ai_ark_m04_login`: `{"a":1e-7}` passed, `{"a":1e0}` failed, and the 14-case selected matrix had **zero mismatches**. The function catalog still reported owner `postgres`, `SECURITY INVOKER`, immutable volatility, and EXECUTE only for the original M04 runtime group and owner. No scratch helper function was installed in this real-schema test. The resulting diagnostic source `/tmp/ai-ark-m04-integrated-validator.sql` has SHA-256 `c967543e4ba80ff33c2db7810502bcab670578cbb3567106c32d238e791cf099`.

This closes only the prototype's helper-permission failure. The real SQL's bundle, record, and full-binding closure functions still reparse retained bytes as `jsonb`; the inlined predicate alone cannot make escaped-U+0000 projections or derived hashes sound. A temporary local insertion of this body into migration `003` was reversed using a targeted patch; its SHA-256 returned to `3993ab838248720f15e3a0766f95eee9e9d0baaac0af0cad3c9762fb98567501`. The manifest remained `09de293bd6132c124c086d4d3e75a357e6867383d36821602c53e5b496a8a991`. The disposable container was stopped and removed. **No complete candidate was frozen**; nested projections, all seven transactional surfaces, exact 180-cell catalog gate, replay, restart, and dump/restore remain unrun. M04 remains **NO-GO**.

Pinned Node `22.23.1` / pnpm `11.7.0` reran `pnpm test:unit -- m04` on the restored local bytes: **191/192 passed, one failed, two unhandled errors**. The failed ledger test raised `M04_FROZEN_MIGRATION_HASH_MISMATCH`; the two imports raised `M04_DATABASE_SCHEMA_INVALID` because the SQL differs from the still-frozen pre-correction source hash. This is an actual failed gate, not a pass or a waiver. No aggregate or recovery gate was attempted on an unchanged final candidate.

### Existing-signature nested projection follow-up

A subsequent scratch projector used the existing `m04_canonical_json(jsonb)` signature with a base64-encoded internal byte payload. It validates the original bytes through the inlined existing-signature predicate, scans root members and array elements without `jsonb`-parsing source bytes, removes root `createdAt`, each `analysisAttempts[]` member's `durationMsOrNull`, `tokenCountsOrNull`, and `providerRequestIdOrNull`, then removes `outputFingerprint` for the second preimage. The same root-member operation removed `id`/`recordFingerprint` and `idempotencyKey` in a synthetic record/request probe. The diagnostic source `/tmp/ai-ark-m04-nested-projection.sql` has SHA-256 `9aee39e159b8703403b9b22e36cd1e177f81f4bc88047edf31384b87b6c6afe8`.

For a synthetic canonical object containing two analysis attempts, `1e-7`, and escaped U+0000, both projected byte strings and SHA-256 values matched pinned Node `JSON.stringify`: logical `546b588543f0fbdeae85b2344d3516315ef17230c6a78f44c4e9c1d284808da9`; output preimage `f2ff66b1ef11ad422b7e8e62b71a76ad3cd52c45f36c0421535673d9b404180e`. The probe then ran through the **real M04 migration schema** and direct `ai_ark_m04_login` session, with only the two existing function bodies replaced inside a fresh isolated database. The scratch `probe` schema was removed; the LOGIN could still call both functions. Catalog inspection found both functions `SECURITY INVOKER`, immutable, and EXECUTE only for the original runtime group and owner. A generated check found all **180/180 expected manifest cells present** for the two actual login roles; this was not an exhaustive no-extra-grants catalog audit.

The repository's genuine M03 fixture was extended with an optional proposal-confidence input, preserving its default behavior and adding the required `LOW_CONFIDENCE` warning when below `0.6`. Pinned Node produced a schema-valid genuine M03 V2 bundle with `1e-7` proposal confidence and non-null attempt duration/token counts/provider request ID. Its 44,319 canonical bytes passed the disposable SQL validator; both SQL projection hashes matched independently calculated Node hashes under `ai_ark_m04_login`. A second schema-valid variant put escaped U+0000 in the excluded provider request ID; its 44,323 bytes passed the same real-schema LOGIN validator and both Node-vs-SQL projection-hash comparisons. A synthetic surviving U+0000 value was covered by the earlier projection probe.

This is **positive Gate A feasibility evidence, not a complete Gate A certificate**: the wrapper is diagnostic, has not preserved the existing serializer's ordinary-call behavior, and its canonical validator has only selected-case/numeric-sampling evidence. The unchanged local migration `003` still has no nested-projection implementation. No seven-surface insert, adapter replay, restart, dump/restore, or hostile transactional test has passed on one final candidate. M04 remains **NO-GO**.

## Proof limit and decision

### Bounded accepted-result closure implementation (2026-10-16)

The local, still-unapplied migration `003` now makes the accepted-result trigger compare `NEW.canonical_payload` directly with the UTF-8 canonical serialization of its closed `ACCEPTED` core. It no longer converts the stored payload through `jsonb` for this comparison. This core contains only fixed literals and relationally constrained hexadecimal IDs; it does not contain source text or the M03 decimal domain. A migration-contract regression test asserts the byte comparison and absence of the old reparse in this trigger. The edited SQL SHA-256 is `950a9a85de7eadde9d6ccb727134247751f3145ca29bbc9b59138b6897620be8`; the frozen ledger still names the older hash, intentionally, because the other byte-sensitive closures have not been corrected and no final candidate is frozen.

Pinned Node `22.23.1` ran the focused `m04-migration.contract.test.ts`: **19/19 passed**; `pnpm typecheck`: **23/23 tasks passed**; and Prettier checked the edited TypeScript/report files. A disposable, network-isolated PostgreSQL 17.6 container applied the rendered real `001`–`003` migrations successfully with the unchanged privilege manifest, proving this SQL edit compiles in the complete schema. A separate `probe` schema extracted the exact edited serializer and accepted-result trigger bodies from `003`, attached the trigger to a minimal matching relation, and used a direct `ai_ark_m04_login` session. A canonical `ACCEPTED` result inserted successfully (`current_user=session_user=ai_ark_m04_login`); a semantically identical JSON document with spaces after commas failed with `M04_ACCEPTED_RESULT_INTEGRITY_INVALID`. The probe relation is narrower than the real seven-surface binding path; it does not demonstrate a complete M04 transaction or catalog-exact runtime ACL. `pnpm test:unit -- m04` remained **failed: 191/192 passed, one frozen-migration-hash failure, two unhandled old-hash import errors**. These failures are expected from the intentionally unrepinned partial SQL, but are not waived.

The bundle, generic record, request, and full-binding closure bodies still reparse retained canonical bytes as `jsonb`. The scratch base64 projector still lacks unambiguous operation separation from ordinary serializer values. This slice does not establish Gate B, full seven-surface persistence, replay, restart, dump/restore, hostile concurrency, or the unchanged-candidate aggregate gates. M04 remains **NO-GO**. The local SQL ledger must be repinned only after a complete correction is stabilized and verified, not as a way to mask the known failures.

These experiments **do not** prove a zero-grant M04 implementation. The follow-up scratch validator covers some canonical lexical cases but not the complete specified domain or a production function boundary. Neither experiment established exhaustive ECMAScript `[0,1]` number acceptance/rejection; nested array/member deletion and canonical reconstruction; all seven persisted surfaces and their derived hashes; transactional hostile-write rejection; restart/dump-restore; or the actual M04 schema/catalog with the frozen 180 cells. The existing `m04_canonical_json(jsonb)` would also need a non-ambiguous internal-operation contract that preserves all proven-safe preexisting calls. The unit gate remains failed on the deliberately partial migration hash; full M04 gates were not run on a final candidate.

Conclusion: PostgreSQL 17.6 has usable raw-byte primitives and an existing-signature invoker channel, so the zero-new-function/zero-new-grant route is **not falsified**. The bounded proof is insufficient to authorize editing migration `003` or to claim M04 GO. The next technical step is a full-domain canonical-byte validator and nested projection design tested against genuine M03/M04 goldens in an isolated database; if that cannot be made coherent within the existing function signatures and authority, prepare a separately reviewed exact amendment rather than silently adding a helper or grant.
