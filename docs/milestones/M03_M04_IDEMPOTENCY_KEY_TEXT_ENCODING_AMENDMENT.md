The eighth amendment requires the M04 persistence boundary to accept all schema-valid canonical request strings, including U+0000, while preserving the exact canonical request bytes. `EvidenceBindingRequestV1Schema` presently accepts any nonempty `idempotencyKey` of at most 200 UTF-8 bytes; it does not reject U+0000 or unpaired UTF-16 surrogates. `PostgresEvidencePersistenceAdapter` sends the raw key as a PostgreSQL text parameter in its advisory lock, replay lookup, and request-association INSERT. Migration `003` stores `m04_binding_requests.idempotency_key` as `text` and compares it with the JSON request value in its closure check. PostgreSQL `text` cannot contain U+0000: a PostgreSQL 17.6 disposable probe of `convert_from(decode('00','hex'),'UTF8')` failed with `invalid byte sequence for encoding "UTF8": 0x00`, before a constraint or trigger could transform the value. Thus an SQL-only change to the canonical-payload predicate cannot make this schema-valid key persist or replay. An unpaired surrogate additionally conflicts with the eighth amendment's invalid-Unicode-scalar rejection rule; JavaScript `TextEncoder` substitutes U+FFFD when measuring it, so the existing byte-length test does not resolve that conflict.

## 2. Narrow supersession and representation

If approved and separately authorized for implementation, this document supersedes **only** the eighth amendment's Section 2 SQL-only edit boundary to permit the necessary M04 request-key validation and adapter encoding/lookup/readback changes, and the `003` SQL constraint/closure changes derived from that representation. It clarifies approved M04 Sections 8–9, 17, and 18 only for the idempotency key's database storage and lock parameter. All other eight-document requirements remain in force, especially original request-byte authority, exact replay/collision semantics, the row-lock grants, manifest/ACL/OID closure, privacy, immutable records, and every-valid-M03-bundle binding.

The public `EvidenceBindingRequestV1.idempotencyKey` remains a nonempty string of at most **200 UTF-8 bytes**, and U+0000 remains valid. Add explicit Unicode-scalar validation: reject unpaired high or low UTF-16 surrogates before byte-length measurement, canonicalization, fingerprinting, database access, or lock acquisition. This narrow restriction resolves the eighth amendment's invalid-scalar conflict; it does not change the M03 schema or serializer. A paired surrogate representing one supplementary scalar remains valid if within the byte bound. Do not trim, normalize, case-fold, reinterpret, or redact any valid key.

The `m04_binding_requests.idempotency_key text` column remains the unique relational key, but its value becomes lowercase hexadecimal encoding of the **original key's UTF-8 bytes**, not the raw key or a hash. This mapping is deterministic, injective, reversible, ASCII-only, and at most 400 characters for the 200-byte input. It distinguishes strings such as the one-byte NUL, the two-character text `00`, and U+FFFD. Database identity must remain byte-exact even when a named nondeterministic collation exists or is used elsewhere in the database: declare this encoded-key column `COLLATE "C"`, require its existing unique constraint/index to inherit that deterministic collation, and use matching byte-exact column equality for every lookup and replay. Do not rely on a database-default or request-parameter collation to establish uniqueness. Validate the effective column and unique-index collations through PostgreSQL catalog OIDs in the migration/restore gates. The adapter applies one shared codec to every database-bound key parameter: advisory-lock hashing, exact-key lookup, INSERT, and any later key-based query. It retains the original key in the canonical request `bytea`, request fingerprint, in-memory exact-request comparison, and unsigned-UTF-8 advisory-lock **ordering**. The semantic-request projection continues to **exclude** `idempotencyKey`, so distinct-key/same-semantic replay is unchanged. The response contract remains unchanged and exposes neither the original nor encoded key. Only the database-bound key argument and stored relational representation change. The advisory lock uses the encoded key as its SQL text argument; identical original keys still acquire the same lock, while the original three-key ordering remains deterministic.

Change only the existing local, unapplied `003` SQL as needed to apply the encoded-key `COLLATE "C"` declaration, constrain the stored encoding to lowercase even-length hex representing 1–200 bytes, and compare it byte-for-byte with the original key represented in the canonical request payload during closure. The closure must not rely on a `jsonb` text extraction that cannot represent U+0000; it must use the eighth amendment's raw-byte-safe canonical parsing/validation path. A direct database write with a mismatched encoded key and request payload must fail before commit. On read/replay, the adapter validates strict lowercase-hex shape and compares the stored encoding to a fresh encoding of the parsed canonical request key; canonical request bytes remain the source of truth. No lossy decode, hash-only equality, or silent replacement is allowed. Preserve the column's `text` type, uniqueness, index count, table/column shape, the 180-cell manifest and all grants, migrations `001` and `002`, and the approved M03 serializer/schema. The existing `003` SQL hash and V2 composite ledger identity must be recomputed after an authorized SQL correction; the manifest hash must not change.
