## 1. Purpose

This document defines how AI ARK will validate its core product thesis before committing to a full-scale engineering and operating program.

It establishes:

- the questions AI ARK must answer;
- the order of validation;
- prototype and concierge research;
- user, creator, tester, and agent recruitment;
- qualitative and quantitative research methods;
- event instrumentation;
- experiment design;
- data quality controls;
- discovery metrics;
- resource-page metrics;
- ranking and verification comprehension;
- workflow metrics;
- creator metrics;
- Labs metrics;
- community-evidence metrics;
- editorial economics;
- API and agent validation;
- Mainland availability validation;
- commercial-signal validation;
- success gates;
- kill and reposition criteria;
- reporting cadence;
- decision authority;
- final MVP scope-freeze process.

The validation plan is intended to prevent two errors:

1. building a large and sophisticated platform before users demonstrate real discovery demand;
2. under-building the product so severely that the differentiated thesis cannot be tested.

## 2. Validation Objective

# Determine whether AI ARK creates meaningfully better capability decisions than GitHub, official directories, social platforms, or generic AI-navigation websites.

The validation program must determine whether users intentionally choose AI ARK because it helps them:

- find useful Resources faster;
- understand what a Resource actually does;
- trust the information;
- compare alternatives;
- understand compatibility;
- understand regional availability;
- follow a practical workflow;
- act with confidence;
- return after use;
- submit useful feedback.

It must also determine whether creators:

- claim their pages;
- correct or improve them;
- share them;
- recruit testers;
- value structured usage evidence;
- prefer AI ARK for a launch or beta.

Finally, it must determine whether the operating model is economically feasible:

- can AI ARK generate high-quality drafts quickly?
- can editors review them efficiently?
- can evidence be maintained?
- can regional status remain current?
- can moderation stay proportionate?
- can the API serve agents reliably?

## 3. Decision Framework

Validation should support one of four decisions.

### 3.1 GO

Evidence supports proceeding to a scoped engineering MVP.

### 3.2 CONDITIONAL GO

The opportunity remains viable, but specific product or operating assumptions require remediation before implementation.

### 3.3 REPOSITION

The broad opportunity remains interesting, but the initial wedge, target user, or value proposition should change.

### 3.4 NO-GO

The evidence does not justify further material investment.

The founder should not allow enthusiasm, sunk cost, design quality, or engineering progress to substitute for validated user value.

## 5. Core Validation Questions

AI ARK should answer twelve primary questions.

### Q1 — Discovery value

Can users find a relevant Resource faster and with greater confidence than through current alternatives?

### Q2 — Resource-page value

Do AI ARK capability dossiers provide enough value beyond a README or directory listing?

### Q3 — Ranking trust

Do users understand and trust Quality Score, Category Rank, Evidence Confidence, and Risk Status?

### Q4 — Verification value

Does AI ARK Verification materially improve selection confidence without being misunderstood as an absolute guarantee?

### Q5 — Workflow value

Are task-oriented workflows more useful than lists of independent Resources?

### Q6 — Creator value

Will creators claim, correct, and share AI ARK pages?

### Q7 — Labs value

Will creators recruit testers through AI ARK, and will testers provide sufficiently structured feedback?

### Q8 — Community-evidence value

Will users contribute meaningful version- and environment-specific reviews?

### Q9 — Editorial economics

Can the URL-to-draft pipeline reduce human review cost without increasing factual risk?

### Q10 — Agent value

Can agents and FounderOS use AI ARK’s structured API to make better capability recommendations?

### Q11 — Mainland value

Do Mainland users value four-level availability information, and can AI ARK maintain it accurately and lawfully?

### Q12 — Commercial value

Is there credible willingness to pay for launch, distribution, analytics, API access, or enterprise intelligence?

## 6. Primary Hypotheses and Falsification

Each hypothesis should specify evidence that would disprove it.

## 6.1 H1 — Better discovery

**Hypothesis:** AI ARK reduces research time and increases confidence.

**Supporting evidence:**

- faster task completion;
- fewer external tabs;
- higher confidence rating;
- meaningful install/source action.

**Falsifying evidence:**

- users immediately leave for GitHub;
- users say AI ARK adds little beyond source summaries;
- time to decision is not improved;
- users cannot explain selection reasons.

---

## 6.2 H2 — Resource dossiers matter

**Hypothesis:** Rich, structured pages are preferred over shallow listings.

**Supporting evidence:**

- users engage with compatibility, prompts, evidence, limitations, or reviews;
- source/install action improves after evaluation;
- users report reduced uncertainty.

**Falsifying evidence:**

- users only use title and source link;
- long pages create confusion;
- important detail sections are ignored;
- users prefer a simpler directory.

---

## 6.3 H3 — Rankings can be trusted

**Hypothesis:** Transparent ranking adds value.

**Supporting evidence:**

- users understand score versus confidence;
- users inspect ranking explanations;
- users change decisions based on evidence quality;
- creators perceive methodology as fair.

**Falsifying evidence:**

- users interpret score as arbitrary;
- users assume sponsorship affects rank;
- category comparison feels invalid;
- creators reject the methodology as opaque or unfair.

---

## 6.4 H4 — Verification changes behavior

**Hypothesis:** Scoped verification improves adoption confidence.

**Supporting evidence:**

- verified Resources receive higher qualified action rates;
- users understand verification levels;
- creators request evaluation;
- users inspect scope and limitations.

**Falsifying evidence:**

- users ignore verification;
- users misunderstand it as absolute safety;
- creators treat it only as marketing;
- evaluation cost exceeds perceived value.

---

## 6.5 H5 — Workflows outperform lists

**Hypothesis:** Users with broad goals value ordered paths.

**Supporting evidence:**

- users open multiple workflow steps;
- workflows receive higher usefulness ratings;
- users save or complete paths;
- users understand expected outputs.

**Falsifying evidence:**

- users prefer a simple list;
- workflows feel generic;
- users replace most recommended Resources;
- workflow completion remains negligible.

---

## 6.6 H6 — Creators value AI ARK

**Hypothesis:** Creators will participate without being paid primarily for attention.

**Supporting evidence:**

- claims;
- corrections;
- page sharing;
- Labs applications;
- launch-program interest;
- creator-provided assets.

**Falsifying evidence:**

- creators do not claim pages;
- creators see no advantage over GitHub;
- creators only participate in exchange for promotion;
- correction and support burden is too high.

---

## 6.7 H7 — Community evidence is obtainable

**Hypothesis:** Users will submit structured reviews when the benefit is clear.

**Supporting evidence:**

- review completion;
- environment details;
- private evidence submission;
- creator responses;
- repeated issue patterns.

**Falsifying evidence:**

- users avoid structured forms;
- reviews remain generic;
- evidence verification is too costly;
- moderation dominates the workload.

---

## 6.8 H8 — Pipeline economics are viable

**Hypothesis:** AI-assisted ingestion can produce trustworthy drafts with low editorial effort.

**Supporting evidence:**

- median URL-to-draft ≤2 minutes;
- median review ≤5 minutes;
- high field acceptance;
- low correction rate.

**Falsifying evidence:**

- review takes >15 minutes;
- claims are often unsupported;
- duplicate detection is unreliable;
- update maintenance is more expensive than initial publication.

---

## 6.9 H9 — API and agent value exist

**Hypothesis:** Machine clients value structured evidence beyond ordinary search.

**Supporting evidence:**

- successful capability discovery;
- workflow resolution;
- FounderOS Connector use;
- repeated API requests;
- positive developer feedback.

**Falsifying evidence:**

- API clients only need search links;
- provenance and ranking are not used;
- integration effort exceeds value;
- clients prefer GitHub or web search directly.

---

## 6.10 H10 — Mainland availability differentiates

**Hypothesis:** Regional truth and alternatives are valuable.

**Supporting evidence:**

- users filter for Mainland availability;
- regional status influences selection;
- alternatives receive engagement;
- creators request China editions.

**Falsifying evidence:**

- users do not trust the status;
- status ages too quickly;
- legal/operational cost is disproportionate;
- few Resources can be meaningfully verified.

## 15. North Star Metric

# Successful Capability Discoveries

A Successful Capability Discovery occurs when:

1. a user or agent expresses discovery intent;
2. AI ARK presents a relevant Resource or workflow;
3. the user or agent evaluates it;
4. a meaningful next action occurs.

Meaningful next actions:

- source opened;
- install command copied;
- Resource saved;
- added to workflow;
- Labs application;
- installation;
- deployment;
- review submitted;
- API recommendation accepted;
- regional alternative selected.

### 15.1 Qualified discovery

Exclude:

- internal staff tests;
- crawlers;
- accidental clicks;
- duplicate rapid clicks;
- promotional traffic without discovery intent.

## 39. Success Gates

## Gate A — Discovery Value

After at least 1,000 qualified sessions:

- result-to-Resource click ≥30%;
- Resource-to-meaningful action ≥15%;
- immediate reformulation <35%;
- ≥20 users report meaningful time savings.

## Gate B — Resource-Page Value

- ≥60% of interviewed users identify information not easily obtained from the source page;
- ≥40% use at least one trust or compatibility section;
- ≥50% report higher decision confidence than with GitHub alone.

## Gate C — Ranking and Verification

- ≥70% understand score versus confidence;
- ≥70% distinguish verification levels;
- ≥80% identify sponsorship correctly;
- ≥60% say verification improves confidence;
- <10% interpret verification as unlimited guarantee.

## Gate D — Workflow Value

- ≥60% rate curated workflow useful;
- ≥20% open or save multiple step Resources;
- ≥10 users complete one meaningful step;
- ≥5 users complete multiple steps;
- ≥1 workflow tested end to end.

## Gate E — Creator Value

- ≥5 creator claims;
- ≥5 creator page shares;
- ≥2 Labs commitments;
- ≥2 launch-program interests;
- ≥1 creator update based on evidence.

## Gate F — Community Evidence

- ≥25 structured reviews;
- ≥10 verified-use submissions;
- ≥5 creator responses;
- ≥2 recurring issues identified;
- no unresolved severe moderation incident.

## Gate G — Editorial Economics

- median URL-to-draft ≤2 minutes;
- median standard review ≤5 minutes;
- material factual correction <5%;
- evidence coverage 100%;
- duplicate precision ≥95%;
- acquisition success ≥95%.

## Gate H — Agent/API Value

- ≥20 successful structured discovery calls;
- ≥10 successful task resolutions;
- one working FounderOS Connector;
- one working MCP client;
- version and freshness present in 100% of Resource responses.

## Gate I — Mainland Value

- ≥20 reviewed statuses;
- ≥5 CN-A3 installation records;
- ≥3 CN-A4 runtime records;
- ≥70% comprehension;
- ≥60% usefulness;
- zero unauthorized mirrors.

## Gate J — Commercial Signal

At least one:

- three paid creator pilots;
- two enterprise or API design partners;
- ten creators willing to pay;
- one distribution partnership.

## 40. Composite GO Decision

A full engineering MVP should require:

- all guardrails passed;
- Gates A, B, G passed;
- at least three of C, D, E, F passed;
- Gate H passed if agent infrastructure remains core;
- Gate I passed or deliberately deferred with documented reason;
- credible commercial signal or explicit decision to validate monetization later.

A single strong vanity metric should not override weak discovery or trust evidence.

## 41. Conditional GO Conditions

A Conditional GO may be issued when:

- discovery value passes;
- editorial economics pass;
- one differentiated feature remains weak but remediable;
- creator or community supply is slower than expected;
- Mainland validation requires legal delay;
- API value is promising but sample is small.

A Conditional GO must specify:

- exact remediation;
- owner;
- deadline;
- re-test threshold;
- scope restrictions.

## 43. Kill Criteria

Stop or materially pause AI ARK if two or more occur:

1. Resource-to-action remains below 10%;
2. users consistently prefer GitHub or official directories;
3. fewer than 8% of activated users return within 30 days;
4. workflows do not improve outcomes;
5. creators do not claim or share pages;
6. review effort routinely exceeds 15 minutes;
7. material factual errors exceed 10%;
8. users do not trust ranking;
9. verification creates confusion or liability disproportionate to value;
10. Labs requires excessive manual recruitment;
11. moderation burden is disproportionate;
12. Mainland status cannot be maintained reliably;
13. agent clients do not value structured API;
14. brand conflict cannot be resolved;
15. AI ARK materially slows higher-priority projects without traction;
16. no credible willingness to pay or strategic integration emerges after validation.

Unsupported, confusing, or disproportionately expensive.

## 51. Scope-Freeze Criteria

A requirement belongs in MVP only when one applies:

- directly supports a passed core hypothesis;
- required for trust or safety;
- required for regulatory or data integrity;
- required for the primary user journey;
- prevents major architectural rework;
- required to measure validation.

It should not enter MVP because:

- it sounds impressive;
- a competitor has it;
- it may matter eventually;
- it is technically interesting;
- it creates more content volume.
