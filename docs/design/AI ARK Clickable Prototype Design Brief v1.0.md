## 1. Purpose

This brief defines the complete scope and execution requirements for the first AI ARK clickable prototype.

The prototype must test whether users understand and value AI ARK as:

> **A trusted discovery and intelligence layer for AI capabilities.**

The prototype should not attempt to demonstrate the entire long-term platform.

It should make the differentiated AI ARK thesis tangible through a coherent set of realistic screens and flows covering:

- task-oriented discovery;
- Skill browsing;
- transparent ranking;
- Resource evaluation;
- scoped verification;
- curated workflows;
- creator identity;
- community usage evidence;
- Mainland availability;
- AI ARK Labs;
- GitHub URL ingestion;
- editorial review.

The prototype should be sufficiently realistic to support:

- moderated usability testing;
- creator interviews;
- founder decision-making;
- concierge validation;
- eventual engineering-kit design.

---

## 2. Prototype Objective

The prototype must answer five questions.

### Q1 — Can users understand what AI ARK is?

Users should understand that AI ARK is not simply:

- a marketplace;
- a GitHub list;
- an AI tools directory;
- a news website.

### Q2 — Can users find a suitable Skill by task?

Users should be able to begin with a goal such as:

> Turn a market report into an investor presentation.

### Q3 — Can users understand why one Resource is recommended over another?

The prototype must communicate:

- Quality Score;
- Category Rank;
- Evidence Confidence;
- Verification;
- compatibility;
- limitations;
- regional availability.

### Q4 — Do workflows add value beyond Resource listings?

Users should understand the sequence of Resources required to complete a broader goal.

### Q5 — Can the backend ingestion concept reduce editorial effort?

The editorial prototype should demonstrate:

```text
GitHub URL
→
Automated analysis
→
Evidence-backed draft
→
Human review
→
Publish
```

## 4. Prototype Boundaries

The prototype must not imply that the following are already production-ready:

- public API self-service;
- public MCP;
- automatic installation;
- automatic execution;
- production payments;
- permanent creator exclusivity;
- broad public AI-generated workflows;
- broad Mainland hosting;
- automatic mirroring;
- general AI news.

Where these concepts appear, label them as:

- coming later;
- private pilot;
- creator application;
- limited test;
- controlled beta.

## 12. Visual Direction

AI ARK should feel:

- editorial;
- calm;
- exact;
- trustworthy;
- contemporary;
- technically credible;
- visually rich without being noisy.

The design should not imitate ColaSkill directly.

It should borrow the design principles of:

- strong curation;
- large visual previews;
- meaningful creator identity;
- restrained color;
- rich long-form Resource pages;
- prominent next actions.

# Direction A — Editorial Atlas

This is the recommended direction.

### Character

- premium editorial publication;
- structured knowledge atlas;
- calm technical confidence;
- visual cards;
- evidence-forward detail pages.

### Background

- warm stone or soft ivory;
- white or slightly elevated content surfaces.

### Typography

- expressive editorial display font for headlines;
- neutral sans-serif for body;
- monospace for commands and evidence identifiers.

### Accent

- deep cobalt;

- muted electric violet.

### Layout

- large centered search;

- asymmetric visual cards;
- generous negative space;
- subtle sticky panels;
- strong section rhythm.

### Trust presentation

- outlined labels;
- compact evidence summaries;
- neutral status icons;

## 15. Design System Foundations

### 15.1 Spacing

Use an 8-point base system.

Suggested scale:

```text
4
8
12
16
24
32
48
64
96
```

### 15.2 Radius

Use:

- 8px for compact controls;
- 12px for cards;
- 16px for large visual panels;
- pill only for statuses and filters.

### 15.3 Borders

- subtle neutral borders;
- avoid heavy shadows;
- use background contrast for hierarchy.

### 15.4 Shadows

Use minimal shadows only for:

- sticky action panel;
- dropdown;
- modal;
- active floating control.

### 15.5 Motion

Use restrained motion:

- hover lift;
- filter transitions;
- accordion;
- progress;
- workflow-step transitions.

Support reduced motion.

## 16. Color Semantics

Color must never be the only indicator.

### Success

Used for:

- verified;
- runtime confirmed;
- resolved.

### Warning

Used for:

- inferred;
- partial;
- expiring;
- update detected.

### Danger

Used for:

- severe risk;
- unavailable;
- revoked;
- blocked.

### Neutral

Used for:

- unknown;
- unreviewed;
- archived;
- not applicable.

### Commercial

Use a separate visual family for:

- Sponsored;
- AI ARK First;
- Launch Partner;
- Exclusive Beta.

Commercial labels must not resemble trust labels.
